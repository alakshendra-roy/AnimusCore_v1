Technical White Paper: Empirical Verification of a 62-Minute Thermal Soak & Deterministic Zero-Allocation Telemetry Architecture

Client POC evaluation harness (poc_eval/poc_eval_harness.cpp) — 153 unattended runs, single host, measured results only.

1.Initialization

The evaluation target was the client-facing POC harness distributed via run_poc_eval.bat, which compiles poc_eval_harness.cpp against the single-header animus.hpp engine with no third-party benchmarking dependency. Prior to the soak, the build entry point was exercised as a client running it for the first time would encounter it.

That first build attempt failed. run_poc_eval.bat's MSVC compilation step passed /Fo:"<path>\" as the object-file output directory — a quoted Windows path ending in a trailing backslash, which cl.exe's argument parser interprets as an escaped quotation mark rather than a path separator. This corrupted the argument boundary and produced fatal error C1083: Cannot open compiler generated file. The fix was a one-line change, doubling the trailing backslash inside the quoted path (the standard Windows-argument-parsing workaround), verified by a clean rebuild before the soak began.

2.Sustained Execution

153 back-to-back runs were executed unattended over 62.1 minutes of wall-clock time. SPSC push-latency P50 held at 21.08 ns for the majority of the run, drifting to a 21.49–21.91 ns band in the final third of the soak window — a small, bounded increase consistent with thermal/scheduler settling under sustained load on a host without dedicated core isolation, not a runaway degradation.

MPMC throughput under 8-producer contention held at a median of 7,471,133 pushes/sec across the full soak, with a measured range of 5,139,660–8,563,594 pushes/sec run-to-run. This variance is consistent with ordinary OS scheduler noise on a non-isolated host and showed no directional decay over the 62-minute window — the minimum and maximum observations were not clustered at either end of the soak timeline.

Zero-allocation verification is enforced by a global operator new/delete watchdog armed only during the timed measurement region of each phase, converting the "no heap allocation on the hot path" claim into a runtime-checked fact for every one of the 153 runs rather than a static assumption carried over from source inspection. Sequence integrity confirms every pushed event was drained by the consumer exactly once, in order, with no loss or reordering, across all 21.3M+ events pushed per run.

4.Outlier Transparency

A single SPSC push-latency sample of ~30.03 ms was recorded during Run #123 (raw_logs/run_0123.log). This is reported here without adjustment because it is real, measured data — and because it is precisely the kind of tail event a soak test exists to surface.

Run populationObserved max latency
Run #123 (1 of 153)~30,030,989.93 ns (~30.03 ms)
All other 152 runs30 µs – 1 ms range
P99.9 across the full soakheld steady at ~39–46 ns

The harness pins threads to exclusive cores and elevates their scheduling priority, but this host is not running kernel-level core isolation (isolcpus, nohz_full, rcu_nocbs — Linux-only mechanisms with no Windows equivalent applied here) or NUMA-pinned allocation. Under those conditions, a pinned thread can still be preempted by the OS scheduler for housekeeping work with nowhere else to run until its one core frees up — which is the documented mechanism behind occasional large tail spikes on a non-isolated host. This single event did not recur, cluster, or trend upward across the remaining runs, and every other correctness and latency metric in Run #123 itself was otherwise unremarkable.
