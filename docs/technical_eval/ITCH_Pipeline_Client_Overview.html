01 — Why This Matters To Your Stack

A feed handler's only job is to not become the bottleneck.

Any component that sits between an exchange feed and your book, risk engine, or analytics layer has one basic obligation: keep up with message bursts without adding its own delay, and without needing constant engineering attention once it's running. These are the three considerations that actually matter when evaluating a component like this — not a sales pitch, just the real questions an infrastructure team asks.

Consideration 1

Predictable latency under load

Every message is parsed with no memory allocation, so one slow allocation can't stall every message queued behind it. See slide 04.

Consideration 2

Resource footprint

The producer and consumer threads benefit from dedicated cores, but neither the decoder nor the ring buffer has any other runtime dependency. See slide 05.

Consideration 3

Integration surface

Decoded records are exposed over shared memory and a plain C interface — existing Python tooling attaches to it; it doesn't get replaced by it. See slide 06.

03 — Parsing Without The Allocator

No message ever waits on a memory allocation.

Every ITCH message — a 12-byte system event or a 40-byte attributed order — is read directly off the wire bytes into one uniform 64-byte record. Nothing in that step touches the heap.

A general-purpose allocator is not instant in the worst case: one unlucky allocation doesn't just slow down the message that triggered it, it stalls every message waiting behind it on a single-file queue. Removing the allocator from this path removes that failure mode, rather than just making it rare. This is instrumented, not assumed — the benchmark overrides the global allocator and counts every call.

04 — Handoff Without Locks

One writer, one reader. Ordinary memory rules do the rest.

The parsing thread and the consuming thread pass records through a shared ring, but neither ever waits on a lock. Each side publishes how far it has gotten; the CPU's own rules for when a write becomes visible to another core handle the rest, at the cost of an ordinary memory write.

The two counters are deliberately kept on separate 64-byte cache lines. Without that separation, the producer updating its counter would invalidate the same line the consumer is reading from, forcing a cross-core cache round-trip on every message.

Scope, stated plainly: this ring is one producer, one consumer, by design — the fastest topology for a direct hand-off. Fanning out to several independent consumers uses a separate broadcast-ring variant already in the codebase, not this one.

05 — Reaching Your Existing Tools

Shared memory, not a serialization layer.

Getting decoded records into a Python risk or analytics process normally means serializing them, sending them over a socket, and deserializing them on the other end. Instead, both processes map the same physical memory page and read it directly — like two programs looking at the same whiteboard instead of mailing each other letters.

07 — Scope & Limitations

What this system is today — stated plainly.

Every constraint below is a scope choice or an open item, not a hidden defect. Each traces to a real file your own engineers can open.

Decoder grade
Reference-grade, not vendor-certified. Verify field offsets against your own copy of the official ITCH 5.0 specification before pointing this at a production feed.
Book state
No order-book reconstruction. This normalizes each message into a flat, uniform record for ring transport — it does not build or maintain a live book.
Test rig
Not a core-isolated benchmark host. Both verified runs used a shared development machine. Sustained throughput and p50/p90 are stable; p99.9/max tail latency should be re-measured on your target hardware.
Ring topology
One producer, one consumer per ring. Multi-consumer fan-out uses a separate broadcast-ring design already present in the codebase, not the SPSC ring described here.
MPID field
Parsed, not carried forward. The Attribution (MPID) field on 'F' messages is read off the wire but not currently included in the normalized record, by scope choice.

Nothing on this page is asserted without a file to check it against — see docs/ARCHITECTURE.md and adapters/itch50/README.md.

Conclusion

What the system does, in one paragraph.

Animus Core's ITCH 5.0 pipeline takes raw exchange bytes and gets them into a normalized, analyzable form without allocating memory, without locking, and without copying data across a process boundary more than once. That behavior has been measured, not assumed, on two independent operating systems and toolchains — ten million messages per run, zero recorded corruption, zero recorded allocation. It is a reference-grade implementation: the architecture is proven, and the scope noted on the previous page is the honest boundary of what has been validated so far.
